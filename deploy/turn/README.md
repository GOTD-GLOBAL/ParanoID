# Offline TURN package candidate

This package implements the build and configuration part of REQ-CALL-006,
RFC-0018 and proposed ADR-0012. It is not deployed. Required retained-allocation
expiry, ACL packet and new network tests remain **NOT RUN** after a platform
interruption. The reviewed source patch and a successful package build do not
establish those missing results or readiness for public deployment.

Run this from an ordinary unprivileged account:

```sh
python3 deploy/turn/build.py \
  --inputs /absolute/pinned-archives --output /absolute/new-output
python3 deploy/turn/package.py /absolute/new-output/release
python3 -m unittest discover -s deploy/turn -p 'test_*.py'
(cd deploy && python3 -m unittest test_turn_environment test_update_environment test_containment)
```

Inputs are the
exact archives in `inputs.json`; there is no downloader, package installation,
server startup, service management or network access in the builder. Output
contains the source/patch build log, regular-file tar, checksums, provenance,
licenses and a relocated loader/version check. Linux x86_64, Python 3.12,
compiler, make, patch, dpkg-deb and readelf are build prerequisites. Runtime
requires Python 3.12, systemd credential support and glibc at least 2.38; the
recorded target had glibc 2.39. OpenSSL and libevent bytes are bundled, with
their exact inputs and ELF dependency closure recorded. Hashes establish
correspondence, not publisher authentication or a bitwise reproducibility claim.

The source archive remains pristine. Only its isolated build copy receives the
exact reviewed [patch](coturn-rest-expiry.patch); before/after file hashes are
checked. Unused upstream example-certificate/man-page symlinks are omitted from
extraction and listed in provenance. The package includes the exact MIT, BSD
and other source notice blocks from coturn headers, alongside dependency
copyright files. [The input manifest](inputs.json) pins every license file;
missing or modified notices stop the build before compilation.

The future reviewed installation layout is `/opt/paranoid-turn/RELEASE`, owned
by root and unwritable by the dedicated unprivileged `paranoid-turn` user.
Instantiate the unit's `@RELEASE@` with the verified manifest release ID.
The system manager reads `/etc/paranoid-turn/relay.secret` through
`LoadCredential`. The launcher validates its private runtime copy, renders only
`/run/paranoid-turn/turnserver.conf` at 0600, and execs the packaged binary with
the config path. Secrets never appear in argv or process environment. Raw
coturn stdout/stderr/file/syslog outputs are suppressed; this package does not
implement aggregate operational counters. `runtime.py check` validates files
and credentials without starting a listener or writing the secret config.

For an offline check with an exclusively owned temporary credential directory,
set `CREDENTIALS_DIRECTORY` to that directory and `RUNTIME_DIRECTORY` to the
literal `/run/paranoid-turn`, then run `python3 -I -B RELEASE/runtime.py check`.
Check mode does not create or inspect `/run/paranoid-turn`; the literal selects
the intended template destination. Use private synthetic test data, not a
deployment secret. `systemd-analyze verify` checks a rendered system unit;
`systemd-analyze --user verify` checks the controller's generated user unit.
Neither command starts or installs a service. Syntax checks do not establish
actual LoadCredential delivery, restart or isolation.

Later installation must create a root-owned private master and separate 0400
relay/root and issuer/messaging-user sources with the same newly generated
64 lowercase ASCII hex bytes, no newline. No secret is bundled or generated by
building. The messaging controller's optional versioned `voice_turn` config and
unit support are documented in `deploy/README.md`. Enabling it requires an
explicitly reviewed same-data server update and matching unit/config change.

After the missing acceptance tests and independent final review pass, a
separately authorized installation must perform these exact file transitions:

| Existing messaging unit file | Generate from the updated controller and prospective config; only the fixed `LoadCredential` line changes |

Use exclusive creation for new secret files, never overwrite, hard-link or pass
their contents as arguments/environment. Confirm the existing messaging UID;
do not invent or change it. Compare secret contents privately without printing.
Building creates none of these accounts, directories or secrets. Retain exact
prior release/config/unit bytes and same-data rollback prerequisites. Do not
expose the relay before credential delivery, peer denial and expiry/drain tests
pass. The current build is not permission to execute these transitions.

The later reviewed activation sequence is: stage immutable relay files/sources;
verify generated unit/config hashes; update the matching messaging server with
its existing same-data controller; install the optional config and generated
user unit; reload only its user manager; apply only approved network policy;
install/reload/start the named relay system unit; restart only the existing
messaging user unit and perform required acceptance. Record each changed file
and prior value for rollback. The firewall manager/effective chain integration
remain unknown here, so no executable firewall step or public-reachability
claim is supplied.

Intended public profile: exact IPv4 157.180.49.125, TCP/UDP 34781 and UDP relay
ports 40000–40015, four allocations per credential, sixteen total, bounded
bandwidth, CLI disabled with `cli=0`, no mobility, unauthenticated STUN or TCP
peer relay. Same-host relay candidates require an external reviewed egress
policy allowing this host's relay ports while denying its other destinations.
The coturn peer-address template alone does not enforce a destination-port
boundary. No firewall rules or packet tests are implemented by this bounded
package subtask. Do not expose this candidate without the missing acceptance
and separately reviewed network/deployment authorization.

Rollback preparation: disable issuer configuration and its credential unit
extension, restart only the existing messaging user unit with its retained
data/TLS, then stop the dedicated relay unit and revert only its approved rules
and release pointer. Preserve the private master for coordinated recovery or
rotate deliberately; never place it in logs or backups published with evidence.
Exact live commands depend on the separately reviewed install preflight and are
not executed here. Existing message data, identity, TLS, DNS and phones remain
outside this package's build actions.

Current offline evidence: 20 controller/feed/containment tests and four
