# RFC-0029: Одноразовый спонсорский инвайт для регистрации ника

## Контекст и решения владельца

Сергей Мальцев, ParanoID Telegram thread 2, 2026-10-05:

- У нового пользователя нет SOL. Сервер оплачивает регистрацию ника.
- Если пользователь пришёл по инвайту — платит сервер, от которого пришёл инвайт.
- Инвайт одноразовый и сгорает после использования.
- Порядок онбординга: сначала ник, потом сервер.
- Скрипты деплоя хранятся в GitHub (open-source модель).

## Открытые вопросы (фиксируем, не решены)

- Привязывать ли токен к конкретному публичному ключу телефона или нет (безликий)?
- Кто пополняет спонсорский кошелёк кастомного сервера: сам владелец покупает SOL или покупает у нас токен → мы конвертируем?
- Utility token как средство платежа за спонсорство — идея, оценивается позже.

---

## Назначение

Позволить владельцу сервера сгенерировать ссылку-приглашение, по которой новый
пользователь без SOL регистрирует ник в Solana-блокчейне за счёт кошелька того
сервера. Ссылка сгорает после первого использования; повторное применение
невозможно.

## Мотивация

- REQ: у нового пользователя на старте 0 SOL.
- Сервер проекта уже платит за регистрацию (RFC-0026 rev. 2026-09-30).
- Для кастомного сервера нужен аналогичный механизм, привязанный к конкретному инвайту.
- Без лимита один инвайт можно использовать для массовой регистрации ников за чужой счёт.

## Цели

- Одноразовый спонсорский инвайт: 1 токен = 1 ник, токен сгорает атомарно с регистрацией.
- Сервер-создатель инвайта спонсирует транзакцию.
- Приложение не хранит и не знает приватный ключ спонсора.
- Работает без домена — только IP и закреплённый TLS-пин.

## Нецели

- Групповые инвайты (один токен = N ников) — за рамками этого RFC.
- Переход на Mainnet — отдельный этап.
- Utility-токен как средство платежа — отдельный этап.

## Дизайн

### Формат инвайт-ссылки

```
https://paranoid.global/i/<server-id>/<invite-token>
paranoid://i/<server-id>/<invite-token>
```

- `server-id` — первые 16 символов hex SHA-256 TLS SPKI-пина сервера
  (та же схема, что в RFC-0028 для `/c/` ссылок).
- `invite-token` — 128-битное случайное значение в base58, сгенерированное
  сервером при создании инвайта; одноразовое.

### Жизненный цикл инвайта на сервере

1. Администратор вызывает `POST /v3/invite/create` (аутентифицированный запрос).
2. Сервер генерирует `token` (16 байт CSPRNG → base58), сохраняет в
   `id_invites(token TEXT PRIMARY KEY, used BOOLEAN NOT NULL DEFAULT false,
   created_at BIGINT NOT NULL, expires_at BIGINT NOT NULL,
   used_by_owner TEXT, used_at BIGINT)` под `ss_meta FOR UPDATE`.
3. Возвращает `{"token": "...", "expires_at": <unix>}`.
4. При использовании токен помечается `used = true` и `used_by_owner = <owner>`
   в той же транзакции, что активирует спонсируемую регистрацию.
5. Повторный запрос с тем же токеном → `409 invite_used` или `404 invite_not_found`.

Срок действия токена: 7 дней (настраивается параметром `PARANOID_INVITE_TTL_DAYS`).

### Флоу на телефоне

```
Телефон получает ссылку /i/<server-id>/<token>
│
├─ Нет ника → онбординг:
│   1. Генерировать ключ (12 слов)
│   2. Придумать ник
│   3. POST /v3/invite/sponsor-prepare  {token, genesis}
│      ← {payer, blockhash, last_valid_height}
│   4. Подписать nik-транзакцию своим ключом (owner)
│   5. POST /v3/invite/sponsor-register {token, owner, name,
│         blockhash, owner_signature}
│      ← {payer_signature}   ← атомарно: токен помечается used
│   6. Телефон собирает транзакцию, персистирует, отправляет в Solana
│   7. Ждёт подтверждения (finalized)
│   8. POST /v3/identity/challenge  → commit → авторизация на сервере
│
└─ Ник уже есть → сразу авторизация:
    POST /v3/identity/challenge → commit
```

**Ключевое отличие от RFC-0026**: `/v3/invite/sponsor-*` потребляет `token` атомарно
с выдачей подписи плательщика. Если телефон упадёт после `sponsor-register`, токен
уже сгорел, но транзакция построена — телефон перепосылает её без нового токена
(persist-before-send, тот же механизм, что в RFC-0026).

### Anti-abuse

| Ограничение | Значение | Где |
|---|---|---|
| 1 токен = 1 ник | атомарная транзакция DB | сервер |
| TTL токена | 7 дней | сервер |
| Лимит токенов на создателя | 20/час, 100/день | сервер |
| Лимит спонсорства на сервер | из RFC-0026: 20/час, 60/день | сервер |
| Минимальный баланс плательщика | 0.02 SOL (из RFC-0026) | сервер |

### Кошелёк спонсора кастомного сервера

Кастомный сервер устанавливается с `--sponsor-keypair` (уже реализовано в RFC-0026).
Владелец сервера пополняет кошелёк вручную переводом SOL. Если кошелёк пуст →
`/v3/invite/sponsor-prepare` возвращает `503 sponsor_empty` → приложение предлагает
пользователю другой сервер или наш общий.

### Общий сервер ParanoID как запасной спонсор

Если инвайт от кастомного сервера, но его кошелёк пуст → приложение автоматически
обращается к нашему общему серверу за спонсорством. Это опциональное fallback-поведение;
по умолчанию выключено, включается только при явной конфигурации (`PARANOID_FALLBACK_SPONSOR`).

## Схема БД (delta к RFC-0028)

```sql
CREATE TABLE id_invites (
  token       TEXT     PRIMARY KEY,
  used        BOOLEAN  NOT NULL DEFAULT false,
  created_at  BIGINT   NOT NULL,
  expires_at  BIGINT   NOT NULL,
  used_by_owner TEXT,
  used_at     BIGINT,
  CONSTRAINT invite_use_consistent
    CHECK ((used AND used_by_owner IS NOT NULL AND used_at IS NOT NULL)
        OR (NOT used AND used_by_owner IS NULL AND used_at IS NULL))
);
```

## Безопасность и приватность

- **Подмена сервера**: сервер-id в ссылке — хеш TLS-пина. Телефон проверяет его
  при TLS-соединении. Поддельный сервер не пройдёт проверку пина.
- **Кража токена**: если токен перехвачен и использован злоумышленником раньше
  легитимного пользователя — ник за его SOL зарегистрирован на чужой ключ. Этот риск
  снижается коротким TTL и привязкой токена к ключу (см. открытый вопрос ниже).
- **Привязка к ключу телефона**: если `sponsor-prepare` принимает публичный ключ
  будущего владельца ника, сервер может сохранить `expected_owner` и отклонить
  `sponsor-register` с другим owner-ключом. Это устраняет кражу токена, но требует
  от телефона уже иметь сгенерированный ключ до первого обращения к серверу.
  **Решение по этому пункту требует подтверждения владельца.**
- **Спам**: лимиты в таблице выше. Один злоумышленник при 20 токенов/час может
  тратить ≈ 0.05 SOL/час со спонсора. Приемлемо для закрытой альфы.
- **Метаданные**: сервер знает, кто кому создавал инвайты и какой ник зарегистрирован
  по каждому инвайту. Это раскрывает социальные связи. Документировать в threat model.

---

## Совместимость

- Сервера без `id_invites` возвращают 404 на `/v3/invite/*` → приложение
  показывает «Этот сервер не поддерживает инвайты» и предлагает прямую регистрацию.
- Инвайт-ссылки `/i/` не мешают контактным ссылкам `/c/` из RFC-0028.
- `install.sh` получает дополнительный параметр `--invite-ttl-days` (по умолчанию 7).

## Открытые вопросы для обсуждения

**OQ-1. Привязка токена к ключу.**
Предложение: `POST /v3/invite/sponsor-prepare` принимает `{token, genesis, owner_pubkey}`.
Сервер сохраняет `expected_owner`. `sponsor-register` с другим owner → 403.
Телефон должен генерировать ключ ДО нажатия кнопки «Занять ник» (уже так и работает).
_Без ответа владельца — не реализовывать._

**OQ-2. Пополнение спонсорского кошелька.**
Вариант А: владелец сервера сам переводит SOL.
Вариант Б: покупает наши токены → мы конвертируем и кладём SOL на его кошелёк.
_Без ответа владельца — реализуем только Вариант А._

**OQ-3. Лимит токенов на инвайт.**
Сейчас: 1 токен = 1 ник. Нужны ли групповые инвайты (1 ссылка = N человек)?
_Без ответа — реализуем только одноразовый._
