## Findings

| ID | Severity | Trigger (actual source) | Minimal correction |
|---|---|---|---|
| **F-01** | **HIGH (blocking as proposed)** | Per-peer durable `events` ledger is capped at 1000 with **no eviction** (`clean_service.rs:242`, enforced again at `:458`), and `validate()` rejects any state exceeding it. A 10-second E2EE heartbeat over 15-minute calls durably records ~90 received events per call per peer. After ~10 long calls with one peer, **every** subsequent inbound message from that peer — including text — permanently fails `invalid_or_full_inbox`. "Fail clear" here means bricking the conversation forever. | Accepted `kind="call"` heartbeats must take a **transient-accept path** in `receive_candidate`: persist the Olm session advance and `cursor = m.sequence`, emit the transient control output, but insert **no** durable `Event` row and queue no receipt. Replay safety is retained by `m.sequence <= s.cursor` (redelivery then fails clear as `conflicting_replay`, which normal `after=cursor` paging never triggers) plus the in-memory per-call `seq`/nonce checks. Recommended: apply the same transient path to **all** accepted call controls; if handshake controls (knock/ready/offer/answer/end, ~3–4 durable rows per call) stay durable, the resulting hard per-peer lifetime budget of roughly 250 calls must be explicitly documented, tested, and surfaced fail-clear. No `State` schema field may be added (rollback to v8 requires `deny_unknown_fields`-clean snapshots). |
| **F-02** | MEDIUM | Outbox is durable, capped at 400, non-evicting, with no unsend API — only `AcceptedV2` after server acceptance (`clean_service.rs:372`, `:813`). Call controls enqueued while offline are transmitted arbitrarily later (stale knocks/heartbeats), pollute the peer's ledger, and can fill the outbox so `outbox_full` blocks **text**. | The call engine enqueues controls only while the realtime lane is connected; at most **one** unaccepted heartbeat outstanding (skip the beat, don't stack); terminate the call locally on `outbox_full` or any enqueue failure; bound total controls per call; receiver drops wall-clock-expired controls (already designed, keep as hint not authority). |

The proposal's authentication core is **sound as designed**: the entire SDP travels inside the strict Olm/PlainV1/Introduction channel whose outer bindings (`v/channel/realm/from/to/id` at `clean_service.rs:495–502`, signed Introduction with recipient account/device/credential/contact binding in `intro_v2.rs`) already exclude server substitution; libwebrtc then enforces the DTLS certificate digest against the `a=fingerprint` of that authenticated remote description. Consequently, **no redundant fingerprint/ICE string fields are needed in the wire format** — the exact SDP bytes are the single authority, cross-validated by the answer's `offer_digest`. The fresh dual-nonce slot design correctly kills restart resurrection (memory-only slots, monotonic deadlines, both nonces required).

## Minimal exact wire/state recommendation (sufficient to implement)

`PlainV1` with `kind:"call"`, body internally tagged, all levels `deny_unknown_fields`:

```json
{"call":{"cv":1,"op":"knock|ready|offer|answer|heartbeat|end",
 "call_id":"<canonical UUIDv4>","caller_nonce":"<base64 of 32 random bytes>",
 "receiver_nonce":"<base64 32B; absent only in knock>",
 "seq":1,"sent_at":1789999999,"ttl":45,
 "sdp":"<UTF-8 ≤6144 bytes; offer/answer only>",
 "offer_digest":"<sha256 hex of exact offered sdp bytes; answer only>",
 "reason":"reject|cancel|hangup|busy|timeout|error (end only)"}}
```

`seq` is monotonically increasing per sender per call (runtime state, starts at 1); `sent_at`/`ttl` are freshness hints only — every deadline uses the local monotonic clock. SDP acceptance constraints, validated on the exact received bytes before `setRemoteDescription`: exactly one `m=audio` and no other m-lines; single BUNDLE group; exactly one sha-256 `a=fingerprint` (consistent if repeated at session/media level); one consistent ice-ufrag/pwd pair; offer `a=setup:actpass`, answer `active|passive` only; `rtcp-mux` required; ≤32 `a=candidate` lines; ≤6 KiB. Calibrate strictness against actual AAR output in tests rather than rejecting unknown-but-standard attributes blindly.

State machine (one active call per device, all slots memory-only, cleared on restart): caller `Idle → Knocked(call_id, caller_nonce, 45s) → Offered(PC created after ready match; gather-complete; offer sent) → Active(answer matches both nonces + offer_digest; DTLS up) → Terminal`; receiver `Idle → Ready(receiver_nonce slot, 45s) → Ringing(offer echoes both nonces) → Active(explicit Answer + RECORD_AUDIO) → Terminal`. Terminal tombstones (call_id → reason) live ≥ max signal TTL. Active terminates on: 30s without a **newly accepted** peer heartbeat (`seq > last`, exact repeats never reset the timer), own 401/revocation, `client.broken()` storage freeze, block, `outbox_full`, ICE disconnect >10s, 15-minute cap.
