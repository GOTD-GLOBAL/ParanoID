## The prekey replay hole — verified concretely in vodozemac 0.10.0 source

The hole is real in the current code once call controls stop writing Event rows, and the prescribed fix is exactly right:

- **Replay reaches the reconstruction branch.** With no Event row for a call control, a replayed exact ciphertext with the same envelope ID and a forged higher server sequence passes both the exact-duplicate lookup (`clean_service.rs:578`) and the `sequence <= cursor` guard (`:588`), reaching `receive_candidate`'s decrypt loop.
- **Retained sessions correctly refuse the replay** — used message keys are deleted: in-order decryption advances the chain (`receiver_chain.rs:191` routes old indices to the skipped-key store only), and consumed skipped keys are removed after use (`receiver_chain.rs:240`), so replay fails with `MissingMessageKey` (`:195`).
- **But the Account happily rebuilds the consumed session.** `create_inbound_session` resolves the one-time key via `find_one_time_key`, which falls through to fallback keys (`account/mod.rs:221-225`), and its cleanup `remove_one_time_key_helper` removes **only** from `one_time_keys`, never fallback secrets (`:242-247`, called at `:324`). With this project's reusable fallback key, the same PreKeyMessage reconstructs an identical session and yields the identical plaintext, unboundedly — accepting the replayed control and burning one of the 8 session slots per replay.
- **The session-ID guard is sound and precise.** `PreKeyMessage::session_id()` (`pre_key.rs:80`) and `Session::session_id()` (`session/mod.rs:239`) both exist and both compute SHA-256(identity_key ‖ base_key ‖ one_time_key) (`session_keys.rs:46-56`) — fully deterministic from the ciphertext, so a replayed prekey matches its retained session's ID exactly, and a genuine new handshake (fresh base key) never collides. Rejecting after all-sessions-decrypt-failure when the prekey's session ID matches any retained session closes the hole with no schema change. The test `retained_session_id_identifies_consumed_reusable_fallback_prekey` (`voice_calls.rs:570-606`) pins precisely this primitive against the real library.

**Does the fix fully close no-Event replay?** Yes, across the asked cases: repeated same prekey (session-ID match → reject, no session created); normal frames (message key consumed → `decryption_failed`); changed envelope ID (inner `p.id != m.id` → `context_mismatch`, candidate state discarded); restart (sessions and cursor are persisted, and `voice_calls.rs:546-567` tests replay after reopen); mixed text (text keeps its durable Event/exact-duplicate ledger unchanged). Two bounded residuals, neither blocking: (1) a prekey whose session was **never retained** (original rejected, candidate discarded) is not caught by the session-ID check, but re-acceptance requires a forged higher sequence from the relay **and** passes only within the 45-second freshness window, and grants no media authority without the fresh volatile nonce handshake plus explicit answer — acceptable, worth one test; (2) rejects advance `cursor` to the forged sequence (`:618`), so a malicious relay can still fail-clear future text — pre-existing v8 behavior, not consent-affecting, correctly outside scope.
