# Final independent security/correctness review — ParanoID overnight-realtime private alpha

## Verdict

- **Product / APK / bundle: PASS** for this exact private synthetic-data alpha handoff, within the documented NOT-RUN boundaries. I found no blocking security or correctness defect in the scoped source, and every security claim I checked against the actual code held.

## Contract verification highlights (all confirmed in code)

- **Non-bearer sessions.** Session context grants nothing without the device-auth signature; `session_proof` (self_service_http.rs:417-469) verifies exactly one Authorization header, a route allowlist, and the Ed25519 signature over the length-prefixed transcript (session_v2.rs:45-61) **before** consuming the nonce; the ledger is mutex-serialized so concurrent duplicates have exactly one winner; 2048-nonce cap with no eviction; replay/malformed/expired fails before any DB query.
- **Immutable binding per operation and final wait.** Every operation and every wait completion re-checks mode/root/device/auth/fingerprint/full stored Credential under the `ss_meta FOR UPDATE` lock (session_query, :479-506), with `still_live` expiry re-checked at the linearization point. Idle waiters use only unlocked hint reads (`wait_needs_query`, :510-530) — the OR-H1 fix is real. Both nested 25-second deadlines exist (inner :137, outer main.rs:255-262) — OR-B1 fixed. 16-socket/8s-handshake/120s-lifetime accept limiter is correct (limited_accept.rs).
- **No arbitrary signer (OR-H2).** `sign_session` (clean_service.rs:625-675) derives method/path/body exclusively from the operation selector: send bodies come only from the durable outbox by ID, GET paths embed the saved cursor, the nonce is native UUIDv4, and both signers refuse any other intent (self_service.rs:250-261 restricts the legacy proof purposes identically, including the exact `/v2/session` extension).
- **Wait/wake correctness.** Subscribe-before-query with re-arm each iteration, 1-second lockless recovery tick, deadline clamped to session expiry, empty/data/revocation completions all via the locked check. The 14 real server tests (706.74s, `14 passed; 0 failed`) cover replay winners, real 301s expiry, 2048 nonces, 64/8 caps, revocation-during-wait, lost-notify recovery, real TLS pool/lifetime, and eight-waiter load (P95 27.404ms vs 27.535ms baseline).
- **Client races/persistence.** RealtimeLoop's generation guards invalidate stale queued work on the single state owner; commit-before-memory persistence with fsync of file and parent directory plus readback (TextEngine.persist); StorageGuard refuses key-without-snapshot; renderer publication precedes receipt network I/O; the single 401 retry (RealtimeLoop.java:117) is safe because sends are idempotent on exact persisted ciphertext and GETs are read-only; the receive-cursor race is closed by the stale-page check (RealtimeLoop.java:168). Fallback is selected only by absent capability, never by a 401. PinnedTls is a strict single-leaf SPKI pin with SAN matching and no trust-all/hostname override.
- **Deployment controller.** `update-v2`/`backup-v2` match the documented contract exactly: preflight before stop, exact unit-fragment/active/enabled/content check, operation+lifecycle locks, exclusive 0600 fsynced key never regenerated, streamed AES-256-GCM with canonical sorted-JSON AAD (re-verified byte-exact on decrypt), full-tag authentication into an anonymous temp file **before** pg_restore, restore only into new `verify_v2_*` DBs, 6-table schema+ordered-row-digest comparison, staged-file and pointer-parent fsync (OR-M5), same-current-data rollback on failure/SIGINT/SIGTERM with exit 130, no stale-dump restore, no fresh-v2/replace-v2/discard reachable from the update path. The legacy `backup()` TLS-key copy is explicitly blocked in v2 mode (alpha.py:377).
- **Evidence-only acceptance runner.** `run-hosted-acceptance.py` + `HostedAcceptanceBridge.java` do what they claim: exactly two synthetic identities, product Java hash-checked against the frozen manifest, direct pinned TLS with proxies stripped, encrypted 0600 local snapshots, reflection reads only public session-context hashes and active GET URL/method (never headers/signatures), no arbitrary signing surface, sanitized failures. Local run is an actual **PASS** (12 samples, P50 85.32ms / P95 103.20ms). `--execute` remains parent-gated; no hosted calls were made.

## Findings

**Blocking (code): none.**

**DEPLOY-GATE-1 (unresolved intermittent; gates live action as a condition, severity medium, availability-only).** Original packaged run: 13/14 PASS, 1 FAIL in `test_same_schema_binary_restarts_with_original_pinned_tls` (deploy/test_v2_update.py:180-195): `wait_health` readiness failure, then the `run` child observed at exit 1. Root cause remains unknown; the failing old-vs-new iteration is unknown; 4 focused replays and the full 11-test order (47.552s) passed with unchanged code and empty captured stderr. I do not call this fixed. Reading the code, the plausible contributors are the fixed timing bounds around startup — `run()`'s 10-second private-PG readiness loop (alpha.py:137-147), the 30-second PG shutdown wait whose overrun would leave a stale `postmaster.pid` (alpha.py:150-156 → refusal at :132), and `wait_health`'s 20-second budget (alpha.py:759-766) — all of which **fail closed** (child exits 1, no data mutation; in live `update_v2` this triggers the tested same-data rollback, worst case a stopped unit with data retained). Smallest meaningful action: one bounded diagnostic — rerun the packaged `test_v2_update.py` with the `run` child's stderr captured to a file (test currently pipes it to DEVNULL at line 186) and record `postmaster.pid` presence plus PG-start elapsed time on failure; alternatively the owner may explicitly accept this as a documented attended-deploy availability risk. One of those two must happen before live `update-v2`.

**Nonblocking observations (no action required tonight):**
- Ed25519 verification runs while holding the `sessions` std mutex on the async runtime (self_service_http.rs:446-460); ~tens of microseconds under a 16-socket cap — acceptable, worth knowing.
- A 429 `waiter_busy` or invalid cursor consumes a session nonce (session_proof runs first); contract-consistent and bounded.
- A wait completing exactly at session expiry returns 401 rather than an empty page; the contract explicitly prefers this.
- Documented-by-design limits: co-resident backup key gives no host-compromise protection; verifier DBs/backups are never auto-purged (disk monitoring needed); shared connection/waiter caps are availability, not fairness; backup causes minutes of downtime.

**Documented NOT-RUNs (correctly not claimed anywhere):** physical phone/OPPO, Doze/force-stop/battery, camera capture, voice, push providers (FCM/UnifiedPush/Huawei), second server, WAN latency, host reboot/power-loss certification, hosted acceptance execution. The 14 historical v7 test failures (+2 old JVM) are exactly preexisting, unchanged, and not represented as fixed. v7 continuity, final-APK server-bytes, and the local acceptance runner are all actual PASS records I inspected.
